# DotAIOS Memory System — External Evaluation & Enhancement Proposal

**Date**: 2026-05-07  
**Sources evaluated**:
1. Chase Hannegan's 3-Step Custom Agentic OS
2. [claude-context](https://github.com/zilliztech/claude-context) (Zilliz) — semantic code search MCP
3. [memsearch](https://github.com/zilliztech/memsearch) (Zilliz) — cross-agent persistent memory

---

## Part 1: What We Have Now

DotAIOS v1.0 memory model:

```
context/          ← always loaded (identity, work, priorities, north-star)
memory/
  events.jsonl    ← append-only state log, agent sees last 50
  signals/        ← classified ephemeral inputs, today+yesterday only
  errors.jsonl    ← failure log
vault/
  wiki/           ← articles, on demand
  org/            ← CRM (companies, people), on demand
  raw/            ← ingested sources
  outputs/        ← generated content
  writing-style.md
```

**How agents find what to read**: The routing table baked into `CLAUDE.md` / `AGENTS.md` / `.cursorrules`. Static rules — "load last 50 events", "load today + yesterday signals", "vault on demand". The agent follows the rules literally.

**What works**: Simple, predictable, zero-dep, any LLM can follow the instructions.

**What doesn't scale**: As the vault and memory grow, the routing table can't answer "which of the 200 wiki articles is relevant to *this* task?" without the agent reading them all or guessing from filenames.

## Part 2: Source-by-Source Evaluation

### Source 1: Chase Hannegan's "3-Step Custom Agentic OS"

**What it is**: A guided prompt that walks users through brain-dumping their daily work → extracting domains → discovering skills → classifying automation triage → producing a CLAUDE.md + skill folder structure. Includes a Streamlit dashboard wrapper.

#### What's interesting

| Idea | Relevance to DotAIOS |
|------|---------------------|
| **Brain dump → domain extraction** workflow | This is basically a more structured version of our `aios init` prompts. The "5 questions per domain" discovery is smart. |
| **Automation triage classification** (on-demand / local-routine / cloud-routine) | We have no runtime classification. Our skills are all implicit "on-demand". A `schedule_type` field in SKILL.md frontmatter would be useful. |
| **Skill → `skill-creator` handoff** (specs only, not full files) | Clever separation. The prompt writes *specs*, delegates *implementation* to a purpose-built tool. DotAIOS could adopt this pattern for plugin scaffolding. |
| **Streamlit dashboard** | Visual cockpit for observability. Nice UX but heavy dependency (Python, Streamlit). |

#### What we should NOT adopt

| Idea | Why not |
|------|---------|
| **Claude Code-only architecture** | The entire system assumes Claude Code. Skills use `/plugin install`, subprocess calls `claude -p`. This is the exact opposite of our agent-universal principle. |
| **Streamlit dashboard** | Adds Python runtime dependency, defeats "zero install" philosophy. If we ever build observability, it should be a static HTML page generated by a CLI command, not a running server. |
| **Permission bypass mode** | `bypassPermissions` flag on subprocess — antithetical to our tiered write-permission model. |
| **Session-based scheduling** (crons inside Claude Code REPL) | Fragile. Only works while Claude Code is running. Not portable across agents. |

#### Verdict

> [!TIP]
> **Cherry-pick the brain-dump → domain → skill discovery workflow as inspiration for a future `aios discover` command.** Everything else is Claude Code-specific infrastructure that conflicts with our values.

### Source 2: claude-context (Zilliz) — Semantic Code Search MCP

**What it is**: An MCP server that indexes a codebase using AST-based chunking, embeds it with OpenAI/Voyage/Ollama, stores vectors in Zilliz Cloud (Milvus), and provides hybrid search (BM25 + dense) to any agent. 10.8k GitHub stars.

#### What's interesting

| Feature | How it could apply |
|---------|-------------------|
| **Hybrid search (BM25 + dense vector)** | This is the gold standard for retrieval. BM25 catches exact keywords, dense vectors catch semantic similarity. Would solve our "which wiki article is relevant?" problem. |
| **~40% token reduction** vs loading full dirs | Directly addresses our scaling concern. As `vault/` grows, efficient retrieval becomes essential. |
| **MCP protocol** = works across Claude Code, Codex, Gemini, Cursor | This is the universal integration layer we've been missing. MCP is the one standard all major agents support. |
| **Incremental indexing via Merkle trees** | Smart — only re-embeds changed files. |
| **AST-based code chunking** | Relevant for code projects, not so much for our markdown memory files. |

#### What's problematic for DotAIOS

| Problem | Why |
|---------|-----|
| **Requires Zilliz Cloud (or self-hosted Milvus)** | Violates local-first. The cloud dependency is the core business model — Zilliz makes money on their managed vector DB. |
| **Requires OpenAI API key** | Another cloud dependency, another API key, another cost. |
| **Designed for code, not personal memory** | AST parsing, code-specific chunking — this is optimized for "find functions that handle auth", not "what are my priorities this week". |
| **Heavy infrastructure** | Node.js MCP server → OpenAI API → Zilliz Cloud. Three moving parts, three potential failure points. |

#### Verdict

> [!IMPORTANT]
> **The retrieval *concept* (hybrid search over personal files) is exactly right. The *implementation* (cloud vector DB + API keys) violates our values.** We should build something that achieves the same goal — efficient context retrieval from `~/aios/` — but with a local-first approach.

### Source 3: memsearch (Zilliz) — Cross-Agent Persistent Memory

**What it is**: A markdown-first memory system with cross-agent plugins. Memories are `.md` files (source of truth). Milvus is a "shadow index" — a derived, rebuildable cache. Supports Claude Code, Codex CLI, OpenClaw, OpenCode. 1.6k GitHub stars.

This one is the most philosophically aligned with DotAIOS.

#### What's genuinely great

| Feature | Alignment with DotAIOS |
|---------|----------------------|
| **"Markdown is the source of truth"** | ✅ Identical to our architecture. `events.jsonl` and context `.md` files are our source of truth. |
| **Shadow index is rebuildable** | ✅ This is the right architecture. The vector index is a *derived* artifact, not the primary store. Delete it and rebuild — zero data loss. |
| **Cross-agent plugins** (Claude Code, Codex, OpenCode, OpenClaw) | ✅ This is exactly the agent-universal approach we need. |
| **Progressive retrieval (3-layer)**: search → expand → transcript | ✅ Brilliant. L1: ranked chunks. L2: full section around the chunk. L3: raw dialogue. Each layer costs more tokens but adds more context. |
| **Auto-capture via stop hooks** | Interesting — auto-summarize each conversation turn and append to daily memory files. |
| **ONNX local embedding (bge-m3)** | ✅ Can run fully offline. No API key, no cost. This is the local-first answer to claude-context's OpenAI requirement. |
| **Milvus Lite** — single-file SQLite-like DB | ✅ `~/.memsearch/milvus.db` — one file, zero server, zero config. This is how a local vector DB should work. |
| **SHA-256 content hashing** for skip-unchanged | ✅ Efficient incremental indexing. |
| **`memsearch watch`** — live file watcher | Keeps the shadow index in sync as files change. |
| **`memsearch compact`** — LLM-powered summarization | Like our planned `aios cleanup` but smarter — summarizes old chunks instead of just deleting them. |

#### What's problematic

| Problem | Analysis |
|---------|----------|
| **Python runtime** | DotAIOS is Node.js/ESM. Adding a Python dependency is a significant complexity jump. Our users may not have Python. |
| **558 MB ONNX model download** | On first run, memsearch downloads the bge-m3 model. This is a big ask for a "quick install" tool. |
| **Milvus Lite still needs Python C extensions** | pymilvus requires compilation. Not trivial on all platforms. |
| **Separate `.memsearch/` directory** | Creates a parallel memory system. We'd have `~/aios/` AND `~/.memsearch/`. Fragmented. |
| **Tight coupling to Zilliz ecosystem** | Despite the local option, the cloud path is the recommended one. The project is ultimately a funnel to Zilliz Cloud. |

#### Verdict

> [!IMPORTANT]
> **memsearch is the closest thing to what DotAIOS needs for memory v2.** The architecture (markdown source of truth + rebuildable shadow index + progressive retrieval + cross-agent plugins) is almost exactly our vision. But we can't *adopt it wholesale* because: (1) Python dependency, (2) 558MB model download, (3) it's a separate product with its own config/directory.
>
> **The right move: study memsearch's architecture and build a lighter version into DotAIOS itself.**

## Part 3: The Cross-Agent Compatibility Question

You raised a critical concern: *"the AIOS needs to work with the same fluency between every model and code agent... I don't know how to properly treat and work with specific skills or plugins built for Claude."*

This is the right instinct. Let me clarify the landscape:

### What agents actually read

| Agent | Auto-loaded file | MCP support | Plugin/skill system |
|-------|-----------------|-------------|-------------------|
| **Claude Code** | `CLAUDE.md` in cwd or home | ✅ Yes (`~/.claude.json`) | Claude Code plugins (proprietary) |
| **Codex CLI** | `AGENTS.md` in cwd | ✅ Yes (`~/.codex/config.toml`) | No plugin system |
| **Gemini CLI** | `AGENTS.md` in cwd | ✅ Yes (`~/.gemini/settings.json`) | No plugin system |
| **Cursor** | `.cursorrules` in cwd or home | ✅ Yes (`~/.cursor/mcp.json`) | No plugin system |
| **Antigravity** | `AGENTS.md` + CLAUDE.md | ✅ Yes | No plugin system |
| **Windsurf** | `.windsurfrules` | ✅ Yes | No plugin system |

### What this means for DotAIOS

**The entrypoint files are already universal.** `CLAUDE.md`, `AGENTS.md`, `.cursorrules` — each agent reads its own file. The content (routing table, memory rules) is the same across all three. ✅ This already works.

**MCP is the universal integration layer.** Every major agent supports MCP. If we build a DotAIOS MCP server, it works everywhere — Claude Code, Codex, Gemini, Cursor, Windsurf. This is the answer to your concern about Claude-specific features.

**Agent-specific skills/plugins are NOT a problem.** Skills in DotAIOS are just markdown files (`SKILL.md`). They're read by whatever agent is running. The agent doesn't care if the skill was "designed for Claude" — it's markdown instructions that any LLM can follow. The `/plan-today` skill works identically in Claude Code, Codex, and Gemini because it's just text.

> [!NOTE]
> **The only Claude-specific feature that doesn't port is the plugin system** (`/plugin install X`). But DotAIOS skills are not Claude plugins — they're agent-readable markdown. Your skills already work universally.

### Where MCP becomes important

MCP is how we add *capabilities beyond file reading*. Right now, agents can only read `~/aios/` files. With an MCP server, agents could:

1. **Search memory semantically** — "find events related to job applications" (instead of reading all 500 events)
2. **Write events** — structured append to `events.jsonl` through a tool call
3. **Query CRM** — "what companies am I in contact with?" without loading all org files

And it works on every agent. That's the unlock.

## Part 4: Concrete Proposal — Memory System v1.1 Enhancements

Based on the analysis above, here's what I recommend. Three layers, each independently useful:

### Layer 1: Context Router (no new deps, v1.1)

**Problem**: The current routing table in CLAUDE.md is static. It says "load last 50 events" but can't say "load events *about this project*".

**Solution**: Add a lightweight context router to `@dotaios/core` that generates a **focused context summary** from `~/aios/` based on the current working directory and task.

```
aios context --for <project-slug>
```

This reads:
- `context/` (always)
- `projects/<slug>/README.md` (if exists)
- `memory/events.jsonl` (last 50, filtered to those mentioning the project)
- `vault/org/` entries referenced in the project

Outputs a single markdown summary the agent can consume. No vector DB, no embeddings — just smart file filtering using grep-like matching.

**This is what memsearch's L1 (search) does, but without embeddings.** For a personal memory system with <1000 files, keyword matching + recency sorting gets you 80% of the way there.

### Layer 2: MCP Server (optional install, v1.2)

**Problem**: Agents can read files but can't search or write to `~/aios/` programmatically.

**Solution**: Build `@dotaios/mcp` — an MCP server that exposes tools:

| Tool | What it does |
|------|-------------|
| `search_memory` | Keyword search across events.jsonl and signals |
| `search_vault` | Search wiki articles and org profiles by name/topic |
| `log_event` | Append a structured event to events.jsonl |
| `get_context` | Return the current context summary (identity + work + priorities) |
| `list_projects` | List active projects with status |

```bash
# User installs once — works for every agent
aios mcp install   # writes to ~/.claude.json, ~/.codex/config.toml, etc.
```

**No vector DB. No embeddings.** Just structured file access over MCP. This is dramatically simpler than claude-context or memsearch, and still solves the core problem: agents can query your memory without reading every file.

> [!TIP]
> This is where the memsearch insight applies: start with keyword search (BM25-equivalent via simple string matching), add semantic search later when vault grows beyond ~500 files.

### Layer 3: Semantic Index (optional, v2.0+)

**Problem**: At scale (hundreds of wiki articles, thousands of events), keyword search fails. You need semantic similarity.

**Solution**: Add an optional `aios index` command that builds a local search index.

**Two options to evaluate later**:

| Option | Pros | Cons |
|--------|------|------|
| **SQLite FTS5** (full-text search) | Zero deps, ships with Node.js, fast, tiny | No semantic search — just keyword/BM25 |
| **Milvus Lite** (via memsearch) | True semantic search, proven | Python dep, 558MB model, complexity |
| **Local ONNX via `onnxruntime-node`** | Semantic search in Node.js, no Python | ~200MB model, complex to ship via npm |
| **Flat-file TF-IDF** | Zero deps, simple | Crude, won't scale past ~1000 docs |

**My recommendation**: Start with **SQLite FTS5 in v2.0**. It's zero-dep (Node.js has `better-sqlite3`), handles BM25 natively, and works for the scale DotAIOS users will actually hit (10s to 100s of files, not millions of lines of code). Semantic search is a v3 concern.

| Enhancement | What | Effort |

## Part 6: Summary — What Each Source Taught Us

| Source | Key takeaway | What we adopt | What we reject |
|--------|-------------|---------------|----------------|
| **Chase Hannegan OS** | Domain → skill discovery workflow is good UX | Skill classification (on-demand/routine), discovery prompts | Claude-only architecture, Streamlit dashboard, subprocess shelling |
| **claude-context** | Hybrid search is the gold standard for retrieval | The *concept* of semantic code/file search via MCP | Cloud vector DB, API key requirements, code-specific design |
| **memsearch** | Markdown source of truth + rebuildable shadow index is the right architecture | Progressive retrieval pattern, cross-agent plugin model, local embedding option | Python dependency, 558MB model, separate product directory |

**The north star**: DotAIOS should become the system where all your agents read the *same personal context* — and eventually search it intelligently — without any cloud dependency, any API key, or any model download on first install. The base layer is files. The search layer is optional. The MCP layer makes it universal.

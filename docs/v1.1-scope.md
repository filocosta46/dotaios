## Candidate Features — Evaluation

### 1. `aios context` — View and edit context files from CLI

**What**: Print the current context (identity, work, priorities) or open them for editing. Think `git config --list` but for your AIOS identity.

**Why it matters**: Right now, after `init`, users have to manually navigate to `~/aios/context/` to update anything. There's no way to check what your agent sees without opening the files. This is the most common "what do I do next?" question after first install.

**UX sketch**:
```bash
aios context                    # show summary of all context files
aios context identity           # print identity.md
aios context work --edit        # open work.md in $EDITOR
aios context --refresh          # re-generate CLAUDE.md/AGENTS.md/.cursorrules from current context
```

| Dimension | Score |
|-----------|-------|
| User value | ⭐⭐⭐⭐⭐ — fills the biggest UX gap after init |
| Effort | 🟢 Small — ~2-3 hours, mostly file reading + `$EDITOR` spawn |
| Risk | Low — no schema changes, no new deps |
| Aligns with vision | ✅ "invisible infrastructure" — makes the context layer inspectable |

---

### 2. `aios upgrade` — Schema migration between versions

**What**: Reads `aios.json` → compares `schema_version` to the CLI's version → runs migration scripts to add new fields/files without destroying existing content.

**Why it matters**: The product brief explicitly calls this out. Without it, v1.1 can't safely add new context files or change the folder structure without users manually diffing. This is the mechanism that makes the product *upgradeable*.

**UX sketch**:
```bash
aios upgrade                    # check + apply migrations
aios upgrade --dry-run          # show what would change
```

| Dimension | Score |
|-----------|-------|
| User value | ⭐⭐⭐⭐ — essential for anyone who installed v1.0 |
| Effort | 🟡 Medium — ~3-4 hours, migration runner + first migration (1.0→1.1) |
| Risk | Medium — must be non-destructive by design |
| Aligns with vision | ✅ Schema versioning is already in `aios.json` — this activates it |

---

### 3. `aios cleanup` — Trim stale memory

**What**: Removes signals older than 30 days. Compacts `events.jsonl` (archives old entries, keeps recent 50 live). Reports what was cleaned.

**Why it matters**: The product brief says agents load "last 50 events" and "today + yesterday signals." Without cleanup, these files grow forever. The cleanup command is the maintenance counterpart to `ingest`.

**UX sketch**:
```bash
aios cleanup                    # trim signals, compact events
aios cleanup --dry-run          # show what would be removed
```

| Dimension | Score |
|-----------|-------|
| User value | ⭐⭐⭐ — not urgent until users have been running for weeks |
| Effort | 🟢 Small — ~2 hours, JSONL line counting + date filtering |
| Risk | Low — operates on append-only logs, easy to test |
| Aligns with vision | ✅ Token-trimmed memory is a core architectural promise |

## Implementation Plan

### Phase 1: Foundation (do first)

**Unit tests** — add `node:test` based tests for core modules before adding new code. This protects existing behavior.

```
tests/
├── core/
│   ├── paths.test.mjs
│   ├── schema.test.mjs
│   ├── manifest.test.mjs
│   └── memory.test.mjs
└── cli/
    └── smoke.test.mjs          # formalize existing smoke into assertions
```

- Test runner: `node:test` (built-in, zero deps, aligns with philosophy)
- Add `"test": "node --test tests/**/*.test.mjs"` to root `package.json`

### Phase 2: New commands

#### `aios context`

New file: [packages/cli/src/commands/context.mjs](file:///Users/filo/Brain/dotaios/packages/cli/src/commands/context.mjs)

Subcommands:
- `aios context` → summary table of all context files (exists? / last modified / first line preview)
- `aios context <name>` → print content of a specific context file
- `aios context <name> --edit` → open in `$EDITOR` (fallback: `vi`)
- `aios context --refresh` → re-render `CLAUDE.md`, `AGENTS.md`, `.cursorrules` from current context values

Core addition: extract the template rendering logic from `init.mjs` into `@dotaios/core/render.mjs` so both `init` and `context --refresh` share it.

#### `aios upgrade`

New file: [packages/cli/src/commands/upgrade.mjs](file:///Users/filo/Brain/dotaios/packages/cli/src/commands/upgrade.mjs)

Logic:
1. Read `aios.json` → get `schema_version`
2. Compare to CLI's `schemaVersion` from `@dotaios/core/schema.mjs`
3. If equal → "Already up to date"
4. If older → run migration chain (1.0.0 → 1.1.0)
5. Update `schema_version` in `aios.json`

Migration registry: [packages/core/src/migrations/](file:///Users/filo/Brain/dotaios/packages/core/src/migrations/)
- Each migration is a function: `(aiosPath) => Promise<string[]>` returning a list of changes made
- First migration (1.0.0 → 1.1.0): add any new context files, update templates

#### `aios cleanup`

New file: [packages/cli/src/commands/cleanup.mjs](file:///Users/filo/Brain/dotaios/packages/cli/src/commands/cleanup.mjs)

Logic:
1. Read `memory/signals/` → delete `.jsonl` files older than 30 days
2. Read `memory/events.jsonl` → if >50 lines, archive older entries to `memory/events-archive.jsonl`
3. Report: "Archived X events, removed Y signal files, freed Z bytes"
4. `--dry-run` flag: report without deleting

## Acceptance Criteria

A user who installed v1.0.0 can:

1. Run `aios upgrade` → their `~/aios/` is migrated to 1.1.0 schema without losing data
2. Run `aios context` → see a summary of their identity, work, priorities
3. Run `aios context work --edit` → their editor opens with `work.md`
4. Run `aios context --refresh` → `CLAUDE.md` is re-generated from current context
5. Run `aios cleanup` → stale signals are removed, events compacted
6. Run `aios cleanup --dry-run` → see what *would* be cleaned without changes
